# ZHANDI 仿《战地5》体验分阶段优化计划

> 文档版本：v1.0  
> 制定日期：2026-08-03  
> 适用项目：`zf-frontend`  
> 技术栈：TypeScript 6 + Three.js + Rapier3D + WebSocket + Vite

## 1. 项目目标与边界

### 1.1 总目标

把当前“功能覆盖较广、表现偏原型”的 Web FPS，优化为一个具备《战地5》核心感受的可持续开发版本。优先还原的不是商业作品的资产数量，而是以下体验支柱：

1. **大规模战场感**：稳定的征服模式、明确的前线变化、友军与敌军共同推进。
2. **扎实枪械手感**：每类武器拥有可辨识的后坐力、弹道、音效和动画反馈。
3. **步兵与载具协同**：兵种职责清楚，坦克、运输与反载具形成克制关系。
4. **动态战场氛围**：烟尘、爆炸、天气、环境音和局部破坏共同塑造压迫感。
5. **可靠的多人对战基础**：服务器权威、状态同步、延迟补偿和断线恢复可验证。
6. **浏览器可承受的性能**：中端桌面设备 1080p 可稳定游玩，并具备可降级画质。

### 1.2 法务与内容边界

- 只借鉴玩法结构、交互逻辑与战场氛围，不直接复制《战地5》的商标、UI 图标、角色、地图、音乐、语音、模型或纹理。
- 武器与二战装备可依据历史资料制作原创资产；所有第三方资源必须记录来源与许可证。
- 对外发布时使用项目自有名称 `ZHANDI`、原创阵营标识与原创视觉语言。

### 1.3 本轮不优先实现

- 64 人正式商用服务器、全球匹配、付费系统、赛季通行证。
- 全地图任意建筑完全破坏。
- 对商业 3A 资产精度的一比一复制。
- 飞机系统、复杂海战、跨平台账号体系。

先做可玩的 **16v16 征服垂直切片**，再评估扩展到 32v32。

## 2. 当前基线审计

### 2.1 已有能力

| 系统 | 当前实现 | 关键文件 | 成熟度判断 |
|---|---|---|---|
| 游戏入口与主循环 | 菜单进入后初始化全部系统，单一 RAF 主循环 | `src/main.ts`、`src/game/GameScene.ts` | 可运行，耦合过高 |
| 玩家控制 | 行走、冲刺、跳跃、蹲伏、体力、FOV、头部摆动、后坐力、坠落伤害 | `src/player/PlayerController.ts` | 原型可玩 |
| 枪械 | STG44、Suomi、MG42、Kar98k；射速、弹匣、换弹、伤害、散布、射线命中 | `src/weapons/*` | 有框架，缺深度和动画 |
| AI | 两阵营共 8 个 Bot，巡逻、追击、攻击、找掩体、重生 | `src/ai/AIBot.ts` | 功能丰富，缺导航与小队战术 |
| 征服玩法 | A/B/C 三点、占领、兵力值流失、胜负条件 | `src/game/ConquestMode.ts` | 基本闭环 |
| 地图 | 120×120 柏林废墟程序化方块建筑、道路、瓦砾 | `src/maps/BerlinRuins.ts` | 灰盒级 |
| 载具 | 吉普、坦克等配置；项目当前生成两辆吉普，可进入和驾驶 | `src/vehicle/VehicleSystem.ts` | 原型级，载具武器无伤害闭环 |
| 战术装备 | 破片、烟雾、闪光弹及效果 | `src/equipment/TacticalEquipment.ts` | 原型级 |
| 天气与昼夜 | 晴、雨、雪、雾、沙尘；粒子与光照变化 | `src/environment/WeatherSystem.ts` | 可演示，缺材质联动 |
| 音频 | WebAudio 合成枪声、脚步、爆炸、命中等，支持 HRTF | `src/audio/AudioSystem.ts` | 占位音频 |
| HUD/UI | 菜单、设置、计分板、准星、血量、弹药、小地图、征服兵力值 | `src/ui/*` | 信息齐全，视觉偏原型 |
| 网络 | WebSocket 位置广播，客户端文件中存在预测/插值/反作弊类 | `src/network/*` | 非权威原型，若干能力未真正接入 |
| 性能 | 性能预算、监控、LOD/实例化类、Vite 手动分包 | `src/performance/*` | 工具存在但未形成闭环 |

### 2.2 已验证基线

- `npm run build` 成功。
- 构建产物中业务包约 **124.72 kB**，Three.js 约 **530.90 kB**，Rapier 约 **2,235.32 kB**（均为压缩前），Rapier gzip 后约 **829.84 kB**。
- 当前无项目自有自动化测试。
- `GameScene.ts` 约 1,600 行，负责初始化、玩法、AI、射击、载具、特效、网络、HUD 和主循环，是首要技术风险。

### 2.3 主要缺口

1. **宣传完成度高于真实完成度**：README 标记“多人同步、预测、服务器验证、反作弊”等已完成，但实际在线链路主要是位置广播。
2. **非固定物理步长**：`PhysicsWorld.step(dt)` 未使用传入 `dt`，物理行为可能随帧率变化。
3. **碰撞不完整**：玩家主要以高度判断落地，灰盒地图视觉物体与 Rapier 世界未形成完整一致的碰撞/导航数据。
4. **主循环耦合**：任何功能扩展都容易引起回归，难以单测、压测和多人复用。
5. **远端玩家直接瞬移**：当前收到更新后直接设置位置，没有可用的快照缓冲与插值。
6. **服务器非权威**：服务器不管理房间、队伍、生命、武器、命中、载具、据点和胜负，无法保障一致性。
7. **地图与角色均为几何体**：没有 GLTF 角色、武器、载具、PBR 材质、骨骼动画或环境资产管线。
8. **音频为程序合成占位**：无法提供接近战争题材所需的层次、距离感、室内外差异和冲击力。
9. **性能优化类存在逻辑风险**：现有 LOD/实例化实现可能错误移除父子关系或生成 100 个未设置矩阵的实例，不能直接用于生产。
10. **缺少质量门禁**：没有 lint、测试、性能回归场景、网络模拟、错误上报与版本化配置。

## 3. 总体推进原则

### 3.1 优先级顺序

`稳定性与架构 → 垂直切片 → 枪械/移动手感 → 征服与AI → 资产/画面/音频 → 载具/破坏 → 权威联网 → 性能压测 → 发布`

### 3.2 阶段准入规则

- 上一阶段的 P0 验收项全部通过，才能进入下一阶段。
- P1 问题可带入下一阶段，但必须登记负责人和处理阶段。
- 每阶段都必须保留：可运行构建、性能采样、回归清单、变更日志。
- 新功能必须配套调试开关，不允许只能靠肉眼猜测状态。

### 3.3 目标平台与性能档位

| 档位 | 参考设备 | 分辨率 | 目标 |
|---|---|---:|---:|
| 低 | 集显/入门独显、8 GB 内存 | 1280×720 | P95 帧时间 ≤ 33.3 ms，30 FPS 稳定 |
| 中 | GTX 1660 / RX 580 级别 | 1920×1080 | P95 帧时间 ≤ 16.7 ms，60 FPS 稳定 |
| 高 | RTX 3060 / RX 6600 及以上 | 1920×1080 | P95 帧时间 ≤ 13.9 ms，画质优先 |

首屏进入菜单目标：缓存后 ≤ 2 秒；首次进入战局目标：普通宽带下 ≤ 8 秒；长任务不能阻塞主线程超过 50 ms。

## 阶段 1：架构解耦与确定性主循环

**目标：** 解决 1,600 行 `GameScene` 单体类，为后续扩展和联网打基础。  
**建议周期：** 1–2 周。

### 任务

#### P0

- 把 `GameScene` 拆为以下层次：
  - `GameApp`：生命周期、菜单、场景切换。
  - `World`：实体注册、查询、销毁。
  - `Simulation`：固定步长玩法和物理更新。
  - `RenderSystem`：插值渲染、相机、特效。
  - `CombatSystem`、`ConquestSystem`、`VehicleSystem`、`AISystem`、`UISystem`。
- 使用固定逻辑步长：模拟 60 Hz，渲染按屏幕刷新率运行，累计器限制追帧次数。
- 统一时间来源，玩法层不再混用 `performance.now()`、`Date.now()` 和 `setTimeout()`。
- 建立明确的游戏状态机：`BOOT → MENU → LOADING → PLAYING → PAUSED → ROUND_END → DISPOSED`。
- 统一资源所有权和 `dispose()`，处理材质、纹理、几何体、CanvasTexture、音频节点和事件监听器。
- 将命中、击杀、占点、爆炸等通信改为类型化事件总线，避免模块互相直接调用内部状态。

#### P1

- 引入轻量 ECS 思路，但不强制使用第三方 ECS：实体 ID + 组件数据 + 系统查询即可。
- 将浏览器 DOM UI 和战斗模拟彻底隔离。
- 增加暂停、失焦、页面隐藏时的时间处理，避免回到页面后物理爆炸。

### 验收标准

- `GameScene` 仅保留编排职责，建议控制在 300 行以内。
- 30/60/120 FPS 下移动 10 秒的距离差异 < 2%。
- 同一输入录制回放 3 次，核心战斗结果一致。
- 每个核心系统可以独立构造并执行单元测试。

### 关键风险

- 不能“大爆炸式重写”。按主循环、战斗、AI、UI 顺序渐进迁移，每次迁移后保持可玩。

- [x] 主循环已拆出 `simulateFixedStep()`，物理、玩家、武器、AI、天气、征服和 HUD 逻辑按固定步长推进。
- [x] Rapier `world.timestep` 显式使用固定 `dt`，不再忽略传入时间步。

- [x] Esc 暂停、页面隐藏和恢复均重置累计器，避免恢复页面后集中追帧。
- [x] 核心玩法回调统一使用 `simulationTimeMs`；网络发送仍使用协议需要的真实时间戳。

## 阶段 3：征服模式、兵种与小队闭环

**目标：** 从“地图里互射”升级为有目标、有职责、有节奏的战局。  
**建议周期：** 2–3 周。

### 任务

#### P0：征服模式

- 明确一局流程：部署 → 倒计时 → 战斗 → 结算 → 重开。
- 完善据点争夺：争夺状态、中立化、占领速度、人数上限、出生保护、前线出生限制。
- 修正阵营归属一致性；当前玩家在征服模式设为盟军，但 TDM 统计中加入 A 队，必须统一。
- 兵力值由服务器/模拟核心统一扣减，死亡、据点优势、载具损失均有事件来源。
- 加入安全出生点选择：敌人距离、视线、爆炸危险、最近占领点。

#### P0：兵种

- 先实现 4 个原型兵种：突击、医护、支援、侦察。
- 每个兵种具有：主武器类别、两件装备、被动能力、补给职责。
- 增加倒地/救援、弹药补给、医疗包、标记/侦察中的核心闭环。
- 取消“出生即拥有全部武器”，改为部署界面选择兵种和有限装备。

#### P1：小队

- 4 人小队、队长命令、队友出生、命令积分、队伍颜色区分。
- 小队补给呼叫或轻量增援，作为高层目标激励。

### 验收标准

- 一局 12–20 分钟能够稳定结束、结算并重新开始。
- 4 个兵种都有不可替代的团队价值，单一兵种选取率不长期超过 45%。
- 出生后 3 秒内被击杀的比例在测试局中低于 5%。
- 据点与兵力值状态在 UI、模拟和日志中完全一致。

## 阶段 4：AI 导航、小队战术与压测替身

**目标：** AI 不再只是追逐玩家，而是能够填充战局、争夺目标并作为联网压测实体。  
**建议周期：** 2–3 周。

### 任务

#### P0

- 基于地图导航网格或 waypoint graph 实现寻路，支持门洞、道路、掩体和不可达检测。
- 把 Bot 改为感知系统 + 决策层 + 动作层：视觉、听觉、最近威胁、目标价值、行动冷却。
- 小队 AI 角色：队长、突击、支援、医护；至少支持跟随、集火、压制、推进、撤退、救援。
- 据点目标选择使用效用评分，考虑距离、友军数量、敌军压力和兵力值。
- 增加 AI LOD：远距离降低感知和决策频率，离屏角色简化动画与碰撞查询。
- 修复 AI 计分板当前随机 Ping 和静态击杀数，所有统计来自战斗事件。

#### P1

- 坦克/车辆 AI、反载具决策、烟雾掩护。
- 难度不通过简单提高命中率作弊，而通过反应时间、误差、沟通和战术水平区分。

### 验收标准

- 16v16 Bot 战局连续运行 30 分钟，无长期卡死；不可达卡死率 < 1%。
- Bot 能自主占点、补给、救援、使用掩体，行为日志可解释。
- 中端目标机上 32 Bot 的 AI CPU 平均预算 ≤ 4 ms/帧，P95 ≤ 8 ms。
- AI 不透视烟雾和实体墙，不在无视线时持续精准追踪玩家。

## 阶段 5：地图、角色与资源管线升级

**目标：** 把程序化灰盒升级为可优化、可迭代的二战废墟垂直切片地图。  
**建议周期：** 3–5 周，可与美术并行。

### 任务

#### P0：资源管线

- 支持 GLTF/GLB、Draco/Meshopt、KTX2/Basis 纹理、骨骼动画和资源清单。
- 所有资源具备：稳定 ID、版本、LOD、碰撞代理、许可证记录、体积预算。
- 分阶段加载：菜单必需 → 玩家/武器 → 近区地图 → 远区细节/音频。
- 引入缓存和失败占位物；移除仅加载纹理的半成品 `AssetPipeline` 设计。

#### P0：地图

- 重做一张原创“欧洲城市废墟”征服地图，3–5 个据点。
- 先做动线灰盒：步兵侧路、载具主路、反载具高点、室内近战区、狙击视线控制。
- 地图结构分区流送：近区完整加载、远区 HLOD、不可见区剔除。
- 静态碰撞、导航、声音区域和渲染数据来自同一地图源，避免视觉与物理脱节。
- 使用 InstancedMesh 合并瓦砾、植被、路障等重复物；禁止当前“遍历每个 Mesh 自动生成 100 个实例”的做法。

#### P0：角色与动画

- 两阵营至少各 1 套原创士兵模型和装备变化。
- 动画状态：待机、8 向移动、冲刺、蹲伏、跳跃、落地、换弹、开火、受击、倒地、救援。
- 第一人称手臂和第三人称角色分离；武器事件通过动画标记驱动。

#### P1

- 材质湿润度、积雪、弹孔贴花、战壕泥地、风吹布料的简化表现。
- 地图光照烘焙或轻量探针系统，减少动态灯数量。

### 验收标准

- 目标地图可完整游玩，所有关键通道都有碰撞与导航验证。
- 近景主武器、角色、载具无明显材质缺失或动画穿模。
- 中画质基准场景 draw calls P95 ≤ 350，动态三角形按场景预算控制；不再沿用当前过低且未经场景验证的 100 draw calls/10 万三角形硬编码预算。
- 首次战局加载和峰值内存符合第 3.3 节目标。

## 阶段 6：战场渲染、特效与音频

**目标：** 用可控成本建立“战争大片感”，而不是只增加粒子数量。  
**建议周期：** 2–4 周。

### 任务

#### P0：渲染

- 使用正确的色彩管理、曝光、色调映射和雾效；定义晴天/阴天/黄昏三套美术基线。
- 阴影采用分级策略：玩家和近处载具高质量，远处关闭或使用 blob/contact shadow。
- 增加动态分辨率和分档像素比，根据 P95 帧时间平滑调整。
- 天气系统与材质联动：雨天湿润、雾天能见度、雪天粒子与地面色调变化。

#### P0：特效

- 建立统一 VFX 池：枪口火焰、曳光弹、火花、尘土、爆炸、烟雾、火焰、弹孔。
- 特效按距离、屏幕占比、重要性分级；离屏立即休眠或回收。
- 烟雾既影响视觉，也进入 AI 感知和玩家标记逻辑。
- 爆炸具备冲击波、相机震动、耳鸣、扬尘和物理冲量，但分别设预算。

#### P0：音频

- 用合法录制/购买素材替换程序合成占位音。
- 枪声分层：机械声、枪口爆发、远场尾音、室内反射、弹壳、呼啸/近失弹。
- 依据空间区域切换室内/室外混响和低通；爆炸按距离产生延迟与频谱变化。
- 添加战场 ambient、远处炮火、载具引擎、语音提示、材质脚步。
- 增加并发数、优先级和虚拟化，防止 32 人枪声压垮音频节点。

### 验收标准

- 玩家闭眼能区分武器类别、枪声大致方向和距离层级。
- 32 个并发战斗实体时无持续音频爆音、明显断裂或节点泄漏。
- 中画质下大规模爆炸不会使 P95 帧时间连续 2 秒超过 25 ms。
- 雾和烟不会只对玩家生效而对 AI 无效。

## 阶段 7：载具、反载具与局部破坏

**目标：** 建立步兵—载具—反载具克制链，补齐《战地》式沙盒战场的关键特征。  
**建议周期：** 3–4 周。

### 任务

#### P0：载具

- 优先实现 1 辆轻型坦克 + 1 辆运输车，暂停继续扩充载具数量。
- 坦克采用轮/履带接地模型或稳定的定制运动学控制，不能继续只对方盒刚体施加巨大 impulse。
- 载具模块化伤害：车体、履带/轮胎、炮塔、引擎；不同角度与武器有装甲修正。
- 炮塔旋转、炮弹弹道、爆炸半径、同轴机枪、弹药与维修形成完整闭环。
- 进入/离开座位、座位切换、被摧毁逃生、载具重生均由状态机控制。

#### P0：局部破坏

- 采用预切片/状态切换，不做任意体素破坏。
- 可破坏对象首批：木门、沙袋、木栅栏、小型掩体、建筑外墙预设块。
- 破坏结果影响碰撞、导航、视线和网络状态；碎片仅客户端表现，不进入长期同步。
- 破坏状态使用稳定对象 ID + bitset/事件日志同步。

#### P1

- 维修工具、反坦克火箭、地雷、载具补给站。
- 火焰蔓延和更多建筑破坏状态。

### 验收标准

- 坦克击中正面、侧面、后部产生可解释且一致的伤害差异。
- 破坏前后渲染、物理、AI 导航和网络一致。
- 载具碰撞在 30/60 FPS 下稳定，不持续翻车或穿地。
- 16v16 战局中载具不长期垄断，步兵存在明确反制手段。

## 阶段 8：权威多人服务器与同步

**目标：** 从位置广播 Demo 升级为可验证的一致性对战。  
**建议周期：** 4–6 周。

### 任务

#### P0：服务器架构

- 将服务器独立为 Node 服务项目/工作区，共享纯 TypeScript 协议和模拟数据定义。
- 服务端权威管理：房间、玩家、队伍、出生、移动约束、血量、射击、装备、载具、据点、兵力值、回合。
- 二进制协议或紧凑序列化，消息带 `protocolVersion`、tick、sequence、ack。
- 固定服务器 tick：先 30 Hz，快照 15–20 Hz；根据压测再调整。
- 房间生命周期：创建、加入、满员、加载、开始、中途加入、断线保留、结束、销毁。

#### P0：客户端网络体验

- 本地玩家：客户端预测 + 输入序列 + 服务器校正 + 平滑误差回收。
- 远端实体：快照缓冲 + 100–150 ms 插值；丢包时短时外推，超时冻结。
- 命中判定：服务端验证射速、弹药、姿态、可见性；对步兵射击加入有限历史回溯。
- Interest Management：按分区、距离和事件重要性发送实体状态。
- 网络模拟面板：延迟、抖动、丢包、乱序、限速。

#### P0：安全

- 输入速率限制、协议 schema 校验、房间权限、异常移动/射速检测。
- 客户端 `AntiCheat` 只能作提示，不能作为信任根；关键结果全部服务器裁决。
- 记录最小化审计日志，避免存储敏感数据。

### 验收标准

- 16v16，模拟 100 ms RTT、30 ms jitter、2% packet loss 时：
  - 无持续瞬移；
  - 本地移动校正 P95 < 0.5 m；
  - 据点、血量、弹药、击杀最终一致；
  - 断线重连可恢复战局。
- 非法射速、无限弹药、超速移动、伪造击杀均被服务器拒绝。
- 单房间服务器 CPU/内存数据可监控，并完成 2 小时 soak test。

## 阶段 9：性能专项与大规模战场压测

**目标：** 把性能从“有优化类”变为“有预算、有数据、有自动降级”。  
**建议周期：** 2–3 周。

### 任务

#### P0

- 使用 Chrome Performance、Three.js renderer info、内存快照建立 CPU/GPU/GC 分析流程。
- 拆解帧预算：模拟、AI、物理、动画、VFX、UI、提交 draw call、GPU。
- 避免每帧分配：Vector、数组、Canvas 更新、临时对象、字符串和事件对象进入池化或复用。
- 小地图、计分板、AI 血条、据点 UI 降频；只在数据变化时写 DOM/CanvasTexture。
- 地图使用视锥剔除、HLOD、实例化、遮挡近似、区块加载。
- AI、动画、网络、音频和粒子全部按距离分级。
- Rapier WASM 延迟加载；菜单不阻塞下载物理包。服务器代码从前端构建彻底隔离。
- 删除/重写当前不安全的 `PerformanceOptimizer.applyLOD/applyInstancing`。

#### P1

- 可选 Web Worker：路径规划、地图预处理、压缩解码；不要盲目把强耦合物理迁移到 Worker。
- 探索 WebGPU 渲染器仅作为实验分支，不阻塞 WebGL2 主线。

### 建议帧预算（中画质 60 FPS）

| 模块 | 平均预算 | P95 上限 |
|---|---:|---:|
| 玩家/战斗模拟 | 1.0 ms | 2.0 ms |
| AI | 2.5 ms | 5.0 ms |
| 物理 | 2.0 ms | 4.0 ms |
| 动画 | 1.5 ms | 3.0 ms |
| 网络处理 | 0.7 ms | 1.5 ms |
| UI | 0.7 ms | 1.5 ms |
| 渲染提交 + GPU | 7.0 ms | 12.0 ms |
| 余量 | 1.3 ms | — |

### 验收标准

- 目标机 1080p 中画质 16v16：平均 ≥ 60 FPS，P95 ≤ 16.7 ms，P99 ≤ 25 ms。
- 30 分钟战局 JS heap 和 GPU 资源无持续单向增长。
- GC 单次暂停 P95 < 4 ms。
- 自动画质降级不频繁抖动，恢复有滞回区间。

## 阶段 11：Alpha、Beta 与上线后闭环

**目标：** 通过真实玩家数据收敛平衡、稳定性和体验问题。  
**建议周期：** 持续进行。

### Alpha（功能完整）

### Beta（内容与平衡）

- 进行 16v16 定期测试。
- 通过遥测调整武器 TTK、兵种选取率、地图热点、载具生存时间和局长。
- 只允许配置平衡改动，避免 Beta 后期重构底层架构。

### Release Candidate

- 2 小时服务器 soak、30 分钟客户端内存测试、多浏览器冒烟、断网恢复、版本兼容测试全部通过。
- 法务资源清单 100% 完成。
- 部署包含回滚、协议版本兼容、静态资源缓存失效策略。

### 上线后核心指标

| 指标 | 目标/观察方向 |
|---|---|
| 客户端崩溃率 | < 0.5% 会话 |
| 服务器异常结束率 | < 0.2% 战局 |
| 中画质性能 | 目标机 P95 ≤ 16.7 ms |
| 网络 | 100 ms RTT 下无持续橡皮筋 |
| 单局时长 | 12–20 分钟 |
| 出生 3 秒内死亡率 | < 5% |
| 兵种选取 | 任一兵种长期不超过 45% |
| 载具平均寿命 | 既不秒毁，也不统治整局；以测试数据校准 |

# 5. 工作流与交付规范

## 5.1 每个功能的 Definition of Done

一个功能只有同时满足以下条件才算完成：

- 玩法逻辑实现，并具有单元/集成测试或可自动回放验证。
- 联网功能明确客户端和服务器权威边界。
- 有调试信息和错误处理。
- 有性能预算，不引入不可解释的 P95 退化。
- 支持 `dispose()` 或生命周期回收。
- 设置项、输入、UI 和音频按需接入。
- 文档和配置说明同步更新。

## 5.2 分支与发布策略

- `main`：始终可构建、可运行。
- 功能分支：一项功能一个分支，禁止把架构重构和大量内容改动混在同一提交。
- 每阶段建立里程碑标签，例如 `m1-foundation`、`m2-infantry-slice`、`m3-conquest`。
- 协议变更必须提升 `protocolVersion`，必要时提供一个版本的兼容窗口。

## 5.3 必备调试工具

- 自由相机/观战相机。
- 实体、碰撞体、导航网格、AI 感知、射线和伤害可视化。
- 固定随机种子与输入录制/回放。
- 网络延迟/抖动/丢包模拟。
- 快速跳转据点、生成 Bot/载具、切换天气、给予装备。
- 性能 HUD 与一键导出采样。

## 最终建议

当前最重要的不是继续增加“功能名称”，而是把已有功能做成真实闭环。建议立即从 **阶段 0 → 阶段 1 → 阶段 2** 开始，前三个阶段完成前，不新增地图、天气类型或武器数量。只有当固定步长、架构拆分、自动测试和两把精修武器全部达标后，后续 AI、载具、画面和联网投入才不会反复返工。
